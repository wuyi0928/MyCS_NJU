# 多人共享记账系统：UML 与 UI 设计初稿

本文件是设计辅助材料，不是实验报告。全部设计由 AI 在本次会话生成，尚未经学生逐项确认；不能把本次 AI 自查称为人工修改。学号姓名沿用实验一报告，提交前请本人核对。

## 1. 依据与范围

依据：用户在本聊天贴出的新版实验二任务书、实验一 report.pdf、chat.txt 中“访谈修订版”REQ-001～REQ-025 及人工审查记录。所提供 requirements.md 明确为首次 AI 初稿，不作为最终业务规则来源。不访问或改写用户远程仓库。

产物：类/组件/状态/时序/用例共 5 种类型的 7 张图（其中状态图、时序图各有两个场景，因此是 **5 种 UML 类型、7 张图**），15 张静态 UI 设计图。所有 .puml 为 PlantUML 源码；UI 由 SVG 图形元素直接绘制，并同场景导出 PNG；没有在 Figma/Pixso 中实际编辑，亦未制作 .fig 文件。SVG 可导入设计工具调整文字、形状和布局。导入后的字体及分组需自行检查。

当前不是可运行的记账系统。HTML 是本地图片浏览目录，按钮为界面设计。UI 使用桌面端 1440×1000 画布；中文微软雅黑、深绿侧栏、浅灰背景、绿色主操作。移动端适配不在本轮产物中。

| 06 用例图 | 行为性 | 三类角色的已确认权限及未定权限边界 |

## 3. 架构与模块职责（设计建议）

采用分层的模块化单体：界面调用统一请求入口，再交给各业务模块，通过数据访问层访问关系数据库。课程原型不需要为这些逻辑模块分别部署独立服务。

| 模块 | 职责 | 主要依赖与理由 |
|---|---|---|
| 身份与授权 | 当前身份、账本范围、角色及对象归属校验 | 放在公共入口；每次操作重新授权，不能仅依赖按钮隐藏 |
| 账本与成员 | 创建、邀请、加入、角色变更、管理员转让、退出 | 依赖事务与日志；成员关系保留历史，避免旧账失去关联 |
| 收支与审核 | 录入、本人维护、撤回重提、审核、驳回、作废、更正 | 依赖预算、调整策略和事务；集中维护状态规则及版本 |
| 预算 | 月总/分类限额、默认提醒和阻止开关 | 提供提交校验接口，具体累计及并发策略等待确认 |
| 查询统计 | 组合筛选、分类/成员/月度统计 | 统一有效记录与调整口径，结算不作为新的收入或支出 |
| 结算 | 月结、快照、锁定、结算单作废重结 | 依赖分摊策略及事务；原始记录和历史快照不覆盖 |
| 分摊与调整策略 | 收支承担、调整效果、跨月归属 | 将待确认规则隔离，确认后可替换算法，不散落在页面中 |
| 日志与导出 | 关键操作追溯、管理员查询及导出 | 成功日志与业务同事务；导出重新校验当前权限和账本 |
| 事务与请求去重 | 请求摘要、幂等结果、版本控制、回滚 | 防止重复点击和响应丢失重复入账，保留时长尚未确定 |

主要数据流：成员提交收支 → 金额/权限/预算校验 → 保存待审核及承担明细 → 管理员审核 → 有效查询统计 → 月结读取明细与调整 → 保存不可覆盖的快照与锁定关联。发现错误则创建独立审核的调整；结算单本身错误则填原因作废并新建结算单。

## 4. 数据存储与一致性建议

建议使用关系数据库（具体选 SQLite、PostgreSQL 或其他产品由后续实现决定）。核心表对应类图；金额存整数分，不用二进制浮点。普通金额合法范围为 1～100000000 分，即 0.01～1000000.00 元。用户密码保存独立盐及安全密码哈希，具体认证方案未定。

成员关系以用户与账本关联，退出标记失效，保留历史外键。账本中不允许有效成员重复；不能取消最后一名管理员，但“不允许多管理员”并非已确认要求。

预算使用账本、月份、类别作用域；月总预算的类别为空。建议为“总预算作用域”设置单独唯一约束或规范化作用域键，避免数据库的 NULL 语义使唯一性失效。这是实现建议，不代表访谈已确定预算冲突优先级。

收支记录保存主状态与版本；更新时按账本、对象、版本和当前状态条件更新。记录、承担明细、成功日志及请求凭据在一个事务内保存。调整也是一笔记录，拥有自己的待审/审核流程，用调整信息指向原记录。已更正标记不改变原金额及主状态。

结算单保存月份与有效/已作废状态；快照包含原记录版本、金额及承担数据的复制值，历史展示读快照而非重新读当前记录。成员差额快照含净额。建议以结算单关联记录推导锁定；旧结算单作废后是否继续锁定属于待确认项，不能自动假定解锁。对旧单作废与重结分别执行事务，重结失败时保留作废单，不自动恢复旧单。

同账本同月使用有效单唯一约束（支持部分唯一索引时以状态过滤；否则使用月份槽位表）兜底。结算以及影响该月集合的新增、审核、作废、调整操作遵守同一账本月份并发协调协议，保证读取集合与提交结果一致，避免读取期间又插入新已审数据。跨月操作按固定顺序获取月份锁以避免死锁。

同账本同请求号唯一。先授权，再读取原请求结果；同号不同请求摘要拒绝。首次执行时通过唯一约束占用请求号，业务、日志和成功凭据同事务保存；重试时返回首次结果。失败事务回滚允许原号重试。保存多久、失败响应缓存策略仍需确认。

## 6. 样例金额，避免跨页面矛盾

统一 2026-10 示例：小林实付生活支出 300；小周实付房租 960；小陈实收公共收入 600。三人对支出和收入均等承担/受益是 **本次 UI 的演示假设，不是已确认需求**。

每人承担支出 420、收入受益 200。净额 = 支出实付 − 支出承担 − 收入实收 + 收入受益：小林 +80，小周 +740，小陈 −820，合计 0；正数应收、负数应付。有效支出合计 1260，收入 600，结余 -660；预算 2000，使用 63%，剩余 740。分类为房租 960、生活 300，预算分别 1000、500，餐饮预算 500。

待审晚餐 120 和清洁用品 80 不纳入上述汇总；已驳回交通费 25 也不计入。页面 05 是另一个“准备更正”的操作场景，调整 20 尚未审核，统计仍为 1260；将来审核后日用品变为有效 280，不能让旧结算快照随之变化。页面列表的顺序是页面组织顺序，不是这些动作已经在真实系统中按顺序发生。

页面 03 用手工承担金额展示三人各 40 的草案，不表示已确认支持某种均摊模式。页面 07 暂以已审核支出为演示累计口径；实际是否计待审由本人确认后统一修改。

## 7. 需要你优先确认和修改的部分

1. 分摊：手工金额/均摊是否支持；非整除余分；收入分配；只读与退出成员是否参与。当前接口与数据结构保留扩展，算法未定。
2. 更正：补记/冲减+正金额是 AI 存储建议；调整归属月份、多次调整限制、已更正记录作废联动仍待确认。
3. 预算：累计是否包含待审、总与分类冲突优先级、并发审核超限处理。不要把示例口径当作已确认规则。
4. 结算：当月有待审是否可结，截止时点，作废后解锁策略，重结时跨期调整依赖。当前禁止直接改已结算原账，单据作废不自动开放编辑。
5. 角色：管理员是否能新增本人收支与自审、多管理员策略、邀请初始角色、转让是否需接收方确认。管理员 UI 未擅自提供普通记账入口；只读不提供管理菜单。
6. 页面细节：此轮展示主要界面；整笔作废、角色选择、退出确认和结算单作废已绘制在第 14 张；第 15 张展示空结果、并发冲突、结算失败与无权限。转让确认等其余细节见补充交互说明，均非可执行交互。
7. 字段与体验：登录注册、账本名称限制、分页/时间边界、导出文件格式、移动端尚未定。REQ-020 性能测试条件与 REQ-023 易用性不因画图而变成已确认。

## 8. AI 使用记录（本次真实过程，等待本人补充判断）

使用场景：根据实验一访谈修订结果生成实验二 UML 和 UI 初稿。生成结果：7 份 PlantUML 源码及对应图片、15 张界面 SVG/PNG、设计说明、补充交互稿及浏览目录。使用工具：本会话 Codex、PlantUML 本地渲染、SVG 矢量设计及同场景 PNG 导出。

AI 自查重点：区分首次初稿与最终访谈；修正角色；保持五主状态；保留已审原账并关联调整；不引入逐人确认结算；校对样例差额守恒；检查文件可渲染和图片可读性。此部分是 AI 自查，不是学生人工修改。

优点（供本人评价）：快速覆盖多模块、统一示例金额与界面风格、提供可编辑源文件，减少从零绘图工作。局限：待确认业务不能由 AI 确认；UI 为矢量静态稿，未在指定设计平台内编辑；尚不能代表真实交互和后端安全已实现；视觉布局和图中关系仍需本人检查。

后续由本人真实补充：具体发现的问题、选定的业务规则、修改原因、修改前后的图片/源码差异。不要编造已经发生的人工审查。可以以本轮为 AI 基线提交，修改后再做独立 Git 提交；如使用 AI 实施修改，注明人提出判断、AI执行修改，不能记作纯手工绘制。

关于工作流：需求基线 → AI 出图 → 自动渲染和一致性检查 → 人检查规则/关系/界面 → 人提出修订 → AI 辅助改图 → 人复核 → Git 保存版本。人的业务确认和设计取舍不能被自动语法验证代替；“只检查校对”的工作流能减少绘制工作，但需要足够明确的需求和可追溯的人工反馈。
